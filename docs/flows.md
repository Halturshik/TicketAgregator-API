# Основные сценарии

## Регистрация

1. Клиент отправляет профиль, email и пароль в `POST /api/auth/register`.
2. API нормализует и валидирует поля, проверяет уникальность email.
3. Пароль хешируется bcrypt до сохранения временной регистрации в Redis.
4. Четырёхзначный код сохраняется на 5 минут и отправляется console mailer.
5. Клиент подтверждает код через `POST /api/auth/register/confirm`.
6. Пользователь создаётся в PostgreSQL, временные данные удаляются.
7. Access JWT возвращается в JSON, refresh JWT — в HttpOnly cookie.

Повторный запрос кода ограничен интервалом 2 минуты. После пяти неверных попыток действует cooldown на 5 минут. Временные данные регистрации хранятся 10 минут.

## Вход и refresh

Вход также двухэтапный: сначала проверяются email/пароль, затем одноразовый код. Access token действует 15 минут, refresh token — 14 дней.

При `POST /api/auth/refresh` старый refresh token атомарно заменяется новым. Повторное использование уже заменённого токена отклоняется. Версия токенов хранится у пользователя: смена пароля увеличивает её и делает прежние JWT недействительными.

Восстановление пароля не раскрывает наличие аккаунта по email. После подтверждения кода новый пароль сохраняется, прежние refresh-сессии удаляются и выдаётся новая пара токенов.

## Поиск предложений

Поиск разделён по виду транспорта:

- `POST /api/search/air`;
- `POST /api/search/railway`;
- `POST /api/search/bus`.

Клиент передаёт города, дату, необязательную обратную дату и количество пассажиров. Допустимы 1–12 пассажиров и даты от текущего дня до 12 месяцев вперёд.

Количество итоговых предложений зависит от горизонта:

| Дата поездки | Количество |
| --- | ---: |
| 0–3 месяца | 52–88 |
| 4–6 месяцев | 31–45 |
| 7–9 месяцев | 19–28 |
| 10–12 месяцев | 6–16 |

### Работа поставщиков

1. API загружает маршрут и справочники из PostgreSQL.
2. Для `atlas`, `nexus` и `vertex` конкурентно выполняются три gRPC-запроса.
3. Сервис поставщиков генерирует общий каталог расписаний и применяет настройки конкретного поставщика: доступных перевозчиков, тариф и ценовой коэффициент.
4. API объединяет одинаковые `schedule_id + fare_type`, выбирая меньшую цену.
5. Выдача балансируется примерно как 40% `non_refundable`, 35% `standard`, 25% `flexible` и сортируется по цене.
6. Результат сохраняется в Redis на 10 минут.
7. Клиент получает первую страницу и затем запрашивает следующие по `search_id`.

По умолчанию страница содержит 10 предложений, максимум — 50. Создание поиска ограничено 10 запросами в минуту для гостя и 20 для пользователя; чтение страниц — 60 запросами в минуту.

Для международной авиации вероятность пересадки равна 35%. Хаб выбирается среди трёх ближайших подходящих вариантов; если подходящего аэропорта нет, создаётся прямой рейс. Каждый сегмент получает отдельный номер рейса. Для обратного направления в 75% случаев сохраняется тот же перевозчик.

Цена предложения уже учитывает всё выбранное количество пассажиров. `price_per_passenger` остаётся ценой одного пассажира. Авторизованный пользователь видит бонус к начислению, гость — такую же сумму с подсказкой о регистрации.

## Создание заказа

Клиент отправляет `search_id`, `trip_option_id`, пассажиров и количество используемых бонусов в `POST /api/orders/`.

API повторно получает выбранное предложение из кеша и не принимает цену, маршрут или поставщика от клиента. Это защищает заказ от изменения данных предложения вручную.

Для каждого пассажира указывается source:

- `self` — авторизованный клиент объявляет пассажира владельцем аккаунта. Переданные ФИО, дата рождения и гражданство используются как snapshot заказа и не изменяют профиль; новый документ после успешной оплаты сохраняется среди документов пользователя;
- `saved` — используется принадлежащий пользователю сохранённый пассажир; данные можно переопределить, а `save_changes` применит изменения после успешной оплаты;
- `new` — новый пассажир, который будет автоматически сохранён только после успешной оплаты.

Гость может использовать только `new` и обязан передать email. Для гостевого заказа создаётся секретный `guest_payment_token`.

### Документы

Документ подбирается по гражданству, возрасту и международности поездки:

| Пассажир и маршрут | Документ |
| --- | --- |
| гражданин РФ, 14+, внутренний | `internal_passport` |
| гражданин РФ, до 14, внутренний | `birth_certificate` |
| иностранный гражданин, внутренний | `foreign_passport` |
| гражданин РФ, международный | `international_passport` |
| иностранный гражданин, международный | `foreign_passport` |

Проверяются формат, допустимость и срок действия на дату поездки. Свидетельство о рождении и иностранный паспорт автоматически получают `verified`. Для российских паспортов mock verification даёт 5% `rejected`; результат детерминирован по fingerprint документа и месяцу проверки. При новом заказе документ проверяется заново, поэтому прежний `verified` не считается бессрочным разрешением.

На каждое направление и каждого пассажира создаётся отдельный билет. Поездка туда-обратно для двух пассажиров создаст четыре билета. Авиапересадка остаётся одним билетом с несколькими сегментами.

Заказ получает публичный номер вида `ABC-12345` и действует 15 минут. Неоплаченные заказы и неиспользуемые записи рейсов удаляются фоновым процессом после окончания срока хранения.

## Оплата

`POST /api/payments/mock` принимает внутренний ID заказа и, для гостя, `guest_payment_token`.

1. Заказ блокируется `FOR UPDATE`.
2. Проверяются владелец, статус `created` и `expires_at`.
3. Mock provider с вероятностью около 3% отклоняет оплату.
4. Payment сохраняется в PostgreSQL.
5. При успехе заказ и билеты становятся `paid`.
6. Для пользователя списываются и начисляются бонусы.
7. Новые пассажиры и документы автосохраняются, а разрешённые изменения существующих применяются.
8. Транзакция фиксируется целиком или полностью откатывается.

Начисление составляет `floor(total_price * 0.02)`. Списать можно не больше половины стоимости и не больше текущего баланса. Для гостя бонусы недоступны.

## История заказов

`GET /api/my/orders/` возвращает только `paid`, `partially_refunded` и `refunded` заказы текущего пользователя. `created` и `expired` не входят в историю.

Страница содержит максимум пять заказов. Для интерфейса «Показать ещё» клиент увеличивает `offset` на пять и добавляет новые элементы к уже отображённым. Доступен фильтр `transport=avia|rail|bus`.

История использует snapshots: изменение сохранённого пассажира или документа не переписывает старые билеты.

## Возврат

Сначала клиент может запросить расчёт условий и суммы возврата, затем выполнить возврат. Можно выбрать конкретные билеты или весь оставшийся заказ.

Тарифы:

- `non_refundable` — возврат запрещён;
- `standard` — 90% при запросе не позднее чем за 72 часа;
- `flexible` — 70% от 24 до 72 часов и 90% раньше 72 часов.

Для выполнения обязателен UUID в заголовке `Idempotency-Key`. Повтор того же запроса с тем же ключом возвращает существующую операцию. Использование ключа с другим набором билетов приводит к ответу `409 Conflict`.

### Распределённое выполнение

1. API создаёт локальную операцию `processing` и переводит билеты в `refund_pending`.
2. Через gRPC вызывается `ExecuteRefund` у исходного поставщика.
3. Поставщик сохраняет результат по ключу идемпотентности в собственной базе данных.
4. При успехе API фиксирует `success`, билеты `refunded`, а заказ `partially_refunded` или `refunded`.
5. При явном отказе операция становится `failed`, билеты снова `paid`.
6. Если время ожидания ответа истекло, API возвращает `processing`, а фоновая горутина повторяет запрос позднее.
7. После восьми попыток или 24 часов операция становится `requires_review`.

`Retry-After` сообщает, когда имеет смысл повторно запросить незавершённую операцию со статусом `processing`.

### Деньги и бонусы

`current_total_price` уменьшается на полную исходную цену возвращённых билетов независимо от комиссии поставщика. Процент тарифа определяет сумму, которую поставщик готов вернуть.

Использованные бонусы пересчитываются так, чтобы на оставшуюся часть заказа по-прежнему приходилось не более 50%. Излишек возвращается на бонусный баланс и вычитается из денежной части возврата. Начисленные бонусы пересчитываются от актуальной стоимости заказа.

Если начисленные за заказ бонусы уже потрачены, баланс не становится отрицательным: недостающая часть записывается как `bonus_debt` и погашается будущими начислениями.

## Гостевой доступ к бронированию

1. `POST /api/bookings/lookup` принимает номер билета или заказа.
2. API возвращает только публичное резюме: маршрут, время, транспорт, количество билетов/пассажиров и замаскированное имя конкретного пассажира при поиске по билету.
3. Гость отправляет тот же номер билета или заказа и email в `/api/bookings/access/request`.
4. Если email принадлежит гостевому заказу, отправляется код и возвращается идентификатор запроса подтверждения `challenge_id`.
5. `/api/bookings/access/confirm` проверяет код и устанавливает HttpOnly `booking_access_token` на 15 минут.
6. С этим cookie доступны детали заказа, расчёт условий возврата и его оформление по публичному номеру.

В деталях имя остаётся сокращённым, а документ показывается только последними четырьмя символами. Авторизованный пользователь может открыть только свой заказ. Ошибка доступа снаружи выглядит как `404`, чтобы не облегчать перебор номеров.

Публичные методы поиска ограничены 20 запросами в минуту на IP.

## Публичный поиск рейса

`POST /api/trips/lookup` работает в двух режимах:

- по `ticket_number` возвращает все сегменты конкретного билета;
- по `route_number + date` возвращает конкретные рейсы этого номера за день.

В выдачу попадают только рейсы, связанные с оплаченными или возвращёнными заказами. Персональные данные, документ, цена и владелец заказа не возвращаются.
